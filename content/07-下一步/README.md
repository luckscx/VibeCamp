# 第 7 章 · 下一步：从"能跑"到"能用"

## 这一章要解决的问题

第一个东西做出来了，然后呢？

## 大纲

### 7.1 三个扩展机制（你的杠杆）

用熟之后，这三个东西能让效率再上一个台阶。

| 机制 | 放哪 | 干什么 | 何时用 |
|---|---|---|---|
| **自定义斜杠命令** | `.codebuddy/commands/` 或 `~/.codebuddy/commands/` | 把常用提示词固化成 `/xxx` | 某个提示词用了 3 次以上 |
| **子代理 Sub-Agent** | `.codebuddy/agents/` 或 `~/.codebuddy/agents/` | 封装角色/流程，可复用 | 有固定套路的任务 |
| **Skills 技能** | `.codebuddy/skills/` 或 `~/.codebuddy/skills/` | AI 自动识别调用，可带脚本和权限白名单 | 想让 AI 自动用上某套规范 |

**Skills vs 斜杠命令的关键区别**（已核实）：

| 特性 | Skills | Slash Commands |
|---|---|---|
| 触发方式 | **AI 自动识别调用** | 用户手动输入 |
| 权限控制 | 支持工具白名单 | 无 |
| 工作目录 | 支持自定义 | 当前目录 |
| 可见性 | 对用户透明 | 用户主动发起 |

### 7.1.1 子代理：为什么它是"上下文瓶颈"的解药

官方文档把子代理称为应对上下文问题**最强大的工具之一**。

**原理**：子代理在**独立的上下文窗口**里跑，读一堆文件，最后只返回一个摘要。主对话的上下文完全不被污染。

```
派个子代理调查一下这个项目的目录结构，
还有看看有没有现成的组件可以复用。
```

**三个内置子代理**（开箱即用，已核实）：

| 子代理 | 特点 | 什么时候被自动用 |
|---|---|---|
| **General-Purpose** | 可读写、可执行、可改文件，能访问所有工具 | 任务需要同时探索和修改、有多个相互依赖的步骤 |
| **Plan** | 只读探索（Read/Glob/Grep/Bash） | **计划模式下**自动调用，用来研究代码库 |
| **Explore** | **严格只读**，不能增删改文件 | 需要搜索文件、分析代码结构时 |

**怎么用**：
```
> /agents                          # 打开管理界面，可视化创建
> 使用 code-reviewer 子代理检查我最近的更改     # 显式调用
> 派个子代理调查一下认证系统是怎么处理 token 的   # 让它自己判断
```

#### 示例 1：让子代理替你读一堆文件，只给你结论

你改完代码想让别人（或 AI）帮你看看，但项目有几十个文件，
全贴给 AI 会把对话撑爆。这时候派子代理：

```
> 派个子代理看看我最近改了哪些文件，检查一下有没有明显的问题
```

**你会看到它这么做**（真实形态，措辞每次不同）：

> 我启动一个子代理来审查最近的更改。
> ● 正在探索 src/ 目录…
> ● 读取 12 个文件…
> ✓ 审查完成
>
> 发现 3 处值得注意：
> 1. `GameBoard.tsx:47` —— 数组越界没有保护
> 2. `useTimer.ts:12` —— 定时器没清理，可能内存泄漏
> 3. `score.ts:88` —— 分数计算可以用 Math.max 简化

**验收点**：你看到的是**结论**，不是 12 个文件的原文。

> 这就是为什么子代理能解"上下文瓶颈"——它读了 12 个文件，
> 但主对话里只多了这几行。

也支持**后台运行**和**恢复**：
```
> 在后台运行 code-analyzer 代理来审查整个代码库
> 恢复代理 abc123 并继续分析
```

### 7.1.2 让 AI 帮你配，别手写

> 这个是官方文档里藏得很深但极其实用的一节。

**你不用记任何配置语法。** 直接问：

```
> 参考 CodeBuddy Code 官方文档，如何把输出调整为中文？
> 参考 CodeBuddy Code 官方文档，创建一个自定义斜杠命令来运行测试
> 参考 CodeBuddy Code 官方文档，如何配置自定义模型提供商？
> 参考 CodeBuddy Code 官方文档，如何配置代理服务器？
> 参考 CodeBuddy Code 官方文档，如何配置 Git Hook？
> 参考 CodeBuddy Code 官方文档，如何配置 MCP 服务器？
```

它会：查官方文档 → 找到配置文件 → 按官方推荐方式改 → **验证语法是否正确** → 告诉你怎么生效。

**官方最佳实践**：
> "让 CodeBuddy 生成配置文件，而不是手动编写，避免语法错误。
> 配置完成后让 CodeBuddy 验证是否正确，确保配置生效。"

#### 示例 2：用了 3 次的提示词，就该存成斜杠命令

假设你每次提修改都要打这么一段：

```
> 我改了代码，请检查一下：1. 有没有明显的 bug 2. 有没有更好的写法
> 3. 改动会不会影响别的地方。不要改我的代码逻辑，只给建议。
```

同一个提示词打到第三次，就该固化。建个文件：

**路径**：`.codebuddy/commands/review.md`

```markdown
请检查我最近的改动，重点看：

1. 有没有明显的 bug（尤其是数组越界、空值、异步竞态）
2. 有没有更简洁的写法
3. 改动会不会影响其他模块

要求：
- 不要直接改我的代码，只给建议
- 每条建议指出具体文件名和行号
- 按严重程度排序
```

**然后就能这么用**：

```
> /review
```

**验收点**：输入 `/` 的时候，列表里出现了 `review`。

> 文件名就是命令名。`review.md` → `/review`，`写测试.md` → `/写测试`。
> 子目录会变成前缀：`.codebuddy/commands/git/提交.md` → `/git:提交`。

#### 示例 3：让 AI 帮你配，别手写

上面这些配置看着麻烦？其实不用自己写。直接说：

```
> 帮我把检查代码这件事做成一个斜杠命令，我叫 /review。
> 要求：检查明显的 bug、建议更简洁的写法、判断会不会影响别的模块。
> 只给建议不要改我的代码。
```

**AI 会帮你**：建目录、写 `.md` 文件、填好参数，然后告诉你做好了。

**验收点**：问它一句「你把这个命令放在哪了」，它会告诉你文件路径。
打开看一眼，确认内容是你想要的意思。

> 这一章的三个机制（斜杠命令、子代理、Skills）**都可以这么配**。
> 想用但不知道怎么配的时候，先问 AI，比自己翻文档快得多。

### 7.2 自定义斜杠命令速成

建一个 `.codebuddy/commands/review.md`：
```markdown
---
description: 审查当前改动
---
请审查这次改动，重点看：
1. 有没有明显的 bug
2. 有没有更简单的写法
3. 用中文回复
```
然后 `/review` 就能用。子目录会自动带前缀：`/frontend:build`

### 7.3 Skills 速成

建一个 `.codebuddy/skills/my-style/SKILL.md`：
```markdown
---
name: my-style
description: 我的项目规范和偏好
allowed-tools: Read, Write, Bash
---

本项目遵循以下规范：
- 用 TypeScript 严格模式
- 组件命名 PascalCase
- 注释用中文
```
**AI 会自动判断什么时候用，不用你手动调用。**

进阶：
- `context: fork` → 在独立子代理里跑，不污染主会话
- `user-invocable: false` → 从 `/` 菜单隐藏，只给 AI 内部用
- `hooks` → 在 Skill 里声明前置/后置检查（Beta，需在 settings.json 开 `allowUntrustedFrontmatterHooks`）

### 7.5 无头模式（批量活）

```bash
codebuddy -p "给所有组件加上中文注释"
codebuddy -p "审查这次提交" --output-format json > out.json
git diff HEAD~1 | codebuddy -p "审查这次提交"
```

### 7.6 什么时候该真的学点编程

不需要为了做东西而学。但这两个信号出现时，学一点会省很多时间：
- 你想改的细节，总是描述不清
- 你开始好奇"它为什么这么写"
