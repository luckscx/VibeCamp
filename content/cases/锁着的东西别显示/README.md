# 案例 · 锁着的东西就别显示出来

> 本案例来自真实项目 **sell_games** 的两个相邻 commit：`f13db7b` 和 `8118c0a`。
> 两个 commit 相隔 **2 分钟**。

## 一句话

界面上摆了 8 个买不起的业务、一堆用不了的升级 —— 全是灰色不可点。
玩家的第一反应是"我好弱"，而不是"我要努力解锁"。

![起步阶段](../assets/起步阶段-家庭工作室.webp)
> 游戏的起步阶段：家庭工作室。资源有限，但目标明确。

## 背景

sell_games 是个经营游戏，玩家从"路边摊"一路做到"太空站"，
中间有 8 个层级的业务（tier）。每个业务还有若干升级项。

**原来的界面逻辑**：所有业务**全部列出来**，没解锁的显示成灰色。

结果是新玩家一进游戏看到这样的列表：

```
┌────────────────────────────┐
│ ✅ 路边摊        Lv.3      │  ← 你有
├────────────────────────────┤
│ 🔒 家庭工作室    ¥800      │  ← 刚好买得起，下一个目标
├────────────────────────────┤
│ 🔒 独立团队      ¥12,000   │  ← 灰
├────────────────────────────┤
│ 🔒 工作室楼层    ¥180,000  │  ← 灰
├────────────────────────────┤
│ 🔒 发行商        ¥2,500,000│  ← 灰
├────────────────────────────┤
│ 🔒 移动帝国      ¥38M      │  ← 灰
├────────────────────────────┤
│ 🔒 太空站        ¥650M     │  ← 灰
└────────────────────────────┘
```

## 出了什么问题

**信息噪音。** 具体三个坏处：

1. **压迫感** —— 一眼看到"还差 6 个层级"，而不是"再赚 800 就行"
2. **看不清目标** —— 不知道现在**该**干什么
3. **界面冗长** —— 手机上要滚很久才能看完

> 这是小白做应用时非常容易犯的错：
> **把所有功能都平铺出来**，觉得"让用户看到全部"是好事。
> 实际效果恰恰相反。

## 怎么改的

### 第 1 个改动（`f13db7b`，07:58）—— 只显示"下一个"

```tsx

  // 已拥有的业务全部保留；未拥有业务只展示顺序上的下一家，后续前置锁定项暂不露出。
  const nextTierIndex = game.tiers.findIndex(tier => !tier.owned);

  return (
    <div className="tier-list">
      {INCOME_TIERS.map((tier, idx) => {
        if (!game.tiers[idx].owned && idx !== nextTierIndex) return null;
        // ...
```

**规则**：已拥有的全显示 + 未拥有的**只显示下一个**。

改完是这样：

```
┌────────────────────────────┐
│ ✅ 路边摊        Lv.3      │
├────────────────────────────┤
│ 🔒 家庭工作室    ¥800      │  ← 唯一的目标，非常清楚
└────────────────────────────┘
```

### 第 2 个改动（`8118c0a`，08:00）—— 升级项同理

**2 分钟后**，作者发现升级列表有同样的问题：

```tsx
const tier = upg.targetTier ? game.tiers.find(t => t.id === upg.targetTier) : null;
const tierOwned = !upg.targetTier || (tier && tier.owned);
// 对应业务尚未解锁的未购买升级不展示；已拥有的升级仍保留，便于查看效果。
if (!owned && !tierOwned) return null;
```

**规则**：没买的、且对应业务还没解锁的升级 → 不显示。
但**已拥有的保留**（玩家要能查看效果）。

注意两处注释都用了同样的话术：**"已拥有的 X 仍保留"**。
这是关键 —— **你已有的东西不该凭空消失**，那会让人以为出 bug 了。

## 这个案例教了什么

### 1. 好改动的三个特征

| 特征 | 这个改动 |
|---|---|
| **小** | 一个 4 行、一个 2 行 |
| **想法清晰** | "只显示下一个" |
| **立刻能验证** | 打开页面看列表变短了没 |

**不要憋大招。** 这种小改动积累起来，产品质感就上去了。

### 2. 改完一个地方，立刻想想"还有没有同样的地方"

这是最有价值的一点。

作者改完业务列表，**2 分钟**就意识到升级列表有同样的问题 ——
然后立刻补上第二个 commit。

> **给新手的习惯**：每改完一处，问自己一句 ——
> **"界面上还有别的地方是同样的毛病吗？"**
>
> 也可以直接问 AI：
> ```
> 这个改动我满意了。现在帮我检查一遍：
> 界面上还有哪些地方存在同样的"展示了用不了的东西"的问题？
> 列出来，先别改。
> ```

### 3. "渐进披露"是个通用原则

这个案例背后的设计原则叫 **渐进披露**（Progressive Disclosure）：
**只在用户需要的时候，展示他们需要的信息。**

适用的场景远不止游戏：

| 场景 | 错误做法 | 正确做法 |
|---|---|---|
| 注册流程 | 一页要填 10 个字段 | 分步，一次填 2-3 个 |
| 设置页面 | 50 个选项全展开 | 常用 5 个 + "高级设置"折叠 |
| 工具应用 | 所有按钮平铺 | 按工作流分组，逐步引导 |
| 表单 | 所有校验错误一起弹 | 聚焦到当前字段 |

### 4. 但也别走到另一个极端

**不要把所有东西都藏起来。** 两个反例：

- ❌ 隐藏了用户**正在找**的功能 → 用户以为不存在，直接走了
- ❌ 已拥有的东西被隐藏 → 用户以为数据丢了

> **判断标准**：
> **"这个东西现在对我有用吗？"**
> 有用 → 显示。没用 → 藏起来，等它变有用。

![决策点](../assets/决策点-岔路.webp)
> 好的界面设计就像这个岔路口：只给你当前需要面对的选择，
> 而不是把整张地图一次性摊开。
