# 案例 · 别用 alert 弹窗，做个会消失的提示

> 本案例来自真实项目 **AutoCard**（异步 PvP 卡牌自走棋）的 commit `5553411`。

## 一句话

AI 用 `alert()` 弹出"升级成功" —— 技术上是完成了需求，体验上很糟糕。

## 背景

AutoCard 是个卡牌游戏。玩家在商店合成卡牌、或者战斗后选升级奖励时，
需要给一个"成功"的反馈。

**AI 的第一版实现**：

```ts
// 升级成功时
window.alert('⬆️ 卡牌升级成功！');
```

**代码能跑，功能也对。** 但…

## 出了什么问题

`window.alert()` 是浏览器**最原始**的弹窗，它有三个致命问题：

| 问题 | 表现 |
|---|---|
| **阻塞** | 弹窗不关，整个游戏**卡住不动** |
| **丑** | 系统样式，跟游戏美术完全不搭 |
| **打断沉浸感** | 正在紧张对战，突然弹出个系统框 |

想象一下：你在打 Boss，千钧一发之际选中升级 ——
屏幕中央"啪"弹出一个灰底白框的 Windows 风格对话框，
游戏静止，等你点"确定"。

**这就是"技术上完成，体验上翻车"。**

## 怎么改的

作者给 AI 提的需求（原话，来自 commit message）：

> 战斗界面选择升级成功**不要用 Web 原生弹窗**，做升级动效表现

注意这句需求的结构 —— **先说不要什么，再说要什么**。
这跟第 3 章讲的"明确列出不要什么"完全对上。

**AI 新建了 `UpgradeEffect.ts`**（101 行）：

```ts
/**
 * 升级成功动效 — 替代 window.alert() 的非阻塞反馈组件。
 *
 * 用于「战斗准备阶段选择升级/合成成功」等场景：卡片以弹入+发光环+短暂停留+上浮淡出
 * 的方式展示提示文案，动画结束后自动从父容器移除，不阻塞任何后续交互。
 *
 * 用法：showUpgradeEffect(this, '⬆️ 卡牌名 青铜 → 白银 升级成功！')
 */
export function showUpgradeEffect(
  parent: Container,
  message: string,
  glowColor = 0xffd700
): void {
```

**动效的四个阶段**（来自 commit message 原文）：

> 弹入 `ease-out-back` + 呼吸停留 + 上浮淡出，~1.7s 自动销毁

1. **弹入**：带 `ease-out-back` 缓动，稍微"过冲"再回弹，有弹性
2. **呼吸停留**：外发光环脉动，吸引注意力
3. **上浮淡出**：往上飘着消失，不突兀
4. **自动销毁**：1.7 秒后自己从画面移除，**不需要点任何东西**

看一下它的注释怎么强调"非阻塞"的：

> 动画结束后自动从父容器移除，**不阻塞任何后续交互**

## 一个隐藏的坑（AI 自己踩了）

commit message 里还记了一句：

> render() 调用顺序调整到动效触发前，避免 `removeChildren()` 清掉刚加入的动效节点

翻成白话：

游戏画面每次刷新会先 `removeChildren()` 清空所有元素再重画。
如果动效**先加进去**、然后 `render()` 清空重画 —— **动效刚出生就被清掉了**。

**解决办法**：把 `render()` 调到动效触发**之前**。

> 💡 这类 bug 特别隐蔽：代码没错、动效逻辑也没错，
> 就是**顺序**错了。表现是"提示一闪就没"或者"根本不出现"。

## 这个案例教了什么

### 1. "不要什么"和"要什么"一样重要

如果只说"加个升级成功的提示"，AI 大概率给你 `alert()` ——
因为这是最简单、最容易想到的做法。

**要这样说：**

```
❌ 加个升级成功的提示

✅ 升级成功时给一个反馈：
   - 不要用 alert / confirm 这类系统弹窗（会阻塞游戏）
   - 用一个非阻塞的动效提示，1.5 秒左右自己消失
   - 样式跟游戏美术统一
```

> 详细的"不要什么"清单见 [第 3 章 · 说清楚需求](../../03-说清楚需求/README.md)

### 2. AI 默认给你"最简单能跑的"，不是"体验最好的"

`alert()` 能跑、代码最短、零依赖。**AI 没有理由不选它** ——
除非你明确告诉它不要。

> **规律**：AI 倾向于给出"最小可用实现"。
> 你想要更好的体验，就得**主动提要求**。

### 3. 一句话需求 → 一个 101 行的组件

对比一下：

| | 代码量 | 体验 |
|---|---|---|
| `alert()` | 1 行 | 阻塞、丑 |
| `UpgradeEffect.ts` | 101 行 | 非阻塞、有动效、统一美术 |

**需求越具体，产出越复杂，但越接近你要的。**

### 4. 值得为"感觉"花时间吗？

有人会说：不就是个提示嘛，能通知到不就行了？

但这是个**游戏**。玩家在意的就是感觉。
而且这个改动只花了 AI 几分钟 —— **成本几乎为零**。

> 💡 让 AI 做体验优化是**性价比最高**的事之一：
> 你描述清楚想要的感觉，它花几分钟写完，你的产品质感立刻不一样。
